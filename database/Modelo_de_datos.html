1. Resumen

La base de datos se organiza en 6 schemas, uno por área de responsabilidad del negocio, en lugar de dejar todas las tablas en public. Cada schema corresponde a los módulos del backend (L3) que lo gestionan, de modo que la capa de datos refleja la arquitectura lógica del sistema.

Solo el backend se conecta a la base, con el usuario de aplicación ecommerce_app. No se usa el administrador postgres. El frontend nunca accede a la base: consume la API a través de NGINX.

2. Diagrama entidad–relación

Cada recuadro sombreado es un schema. auth.users es el centro del modelo: 6 de las 10 llaves foráneas apuntan a ella.

3. Schemas y tablas

auth Identidad y acceso Privado

Concentra los datos más sensibles del sistema: contraseñas cifradas y roles. Al estar separado se puede restringir quién lo lee y protegerlo con permisos propios, sin afectar al resto.

4. Claves y relaciones

Todas las tablas tienen una clave primaria id autoincremental. Hay 10 llaves foráneas; 7 de ellas cruzan de un schema a otro. Las reglas de borrado siguen el valor del dato: el historial de ventas se protege, y lo que solo tiene sentido junto a su padre se borra con él.

Tabla (FK)ColumnaReferencia (PK)CardinalidadAl borrar el padre

sales.ordersuser_idauth.users.id1 usuario : N pedidosRESTRICT – No se puede borrar un usuario con pedidos
sales.order_itemsorder_idsales.orders.id1 pedido : N ítemsCASCADE – El detalle se borra con su pedido
sales.order_itemsproduct_idcatalog.products.id1 producto : N ítemsSET NULL – El ítem conserva nombre y precio
sales.paymentsorder_idsales.orders.id1 pedido : 0..1 pagoRESTRICT – Un pedido pagado no se puede borrar

storage.filesuploaded_byauth.users.id1 usuario : N archivosRESTRICT – No se puede borrar un usuario con archivos

Restricciones únicas: auth.users.email, catalog.categories.name y sales.payments.order_id.

5. Schemas privados y de lectura pública

Usuario de PostgreSQLQuién lo usaQué puede hacer
ecommerce_appEl backend (L3)Dueño de los 6 schemas: lee y escribe en todos
ecommerce_consultaReportes o consultas externasSolo leer el schema catalog. No entra a los demás ni puede modificar nada
postgresAdministrador de L4Administración. No lo usa la aplicación

Los schemas auth, sales, storage, messaging y audit son privados: ningún otro usuario puede entrar. catalog es de lectura pública porque es la única información que la tienda muestra sin iniciar sesión. El usuario de consulta se crea con el script database/permisos.sql, que ejecuta el administrador.

Demostración, conectado como ecommerce_consulta:

SELECT * FROM catalog.products;                        -- funciona
SELECT * FROM auth.users;                              -- ERROR: permiso denegado al schema auth
INSERT INTO catalog.categories (name) VALUES ('x');    -- ERROR: permiso denegado

6. Consultas para comprobar la estructura

Sirven en el Query Tool de pgAdmin, en DBeaver o en psql, por si el árbol de pgAdmin no carga.

Schemas, su dueño y su descripción

SELECT n.nspname AS schema,
       pg_get_userbyid(n.nspowner) AS dueno,
       obj_description(n.oid, 'pg_namespace') AS descripcion
FROM pg_namespace n
WHERE n.nspname NOT LIKE 'pg_%' AND n.nspname <> 'information_schema'
ORDER BY 1;

Tablas de cada schema

SELECT table_schema AS schema, table_name AS tabla
FROM information_schema.tables
WHERE table_schema IN ('auth','catalog','sales','storage','messaging','audit','public')
ORDER BY 1, 2;

Columnas de una tabla

SELECT column_name AS columna, data_type AS tipo, is_nullable AS admite_nulo, column_default AS valor_defecto
FROM information_schema.columns
WHERE table_schema = 'sales' AND table_name = 'orders'
ORDER BY ordinal_position;

Llaves foráneas y regla de borrado

SELECT tc.table_schema || '.' || tc.table_name   AS tabla,
       kcu.column_name                           AS columna,
       ccu.table_schema || '.' || ccu.table_name AS referencia,
       rc.delete_rule                            AS al_borrar
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.constraint_column_usage ccu ON tc.constraint_name = ccu.constraint_name
JOIN information_schema.referential_constraints rc ON rc.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
ORDER BY 1, 2;

Atajos en psql

\dn+                  -- lista de schemas con permisos y descripción
\dt auth.*            -- tablas del schema auth (cambiar por catalog, sales...)
\d sales.orders       -- columnas, claves y relaciones de una tabla

Datos de ejemplo cruzando schemas

-- Pedidos con el cliente (auth), el producto (catalog) y el pago (sales)
SELECT o.id AS pedido, u.name AS cliente, i.product_name AS producto,
       i.quantity AS cantidad, o.total, o.status, p.method AS pago
FROM sales.orders o
JOIN auth.users u            ON u.id = o.user_id
JOIN sales.order_items i     ON i.order_id = o.id
LEFT JOIN sales.payments p   ON p.order_id = o.id
ORDER BY o.id;

-- Últimas operaciones registradas y qué instancia las atendió
SELECT a.created_at, u.email, a.method, a.path, a.status_code, a.instance
FROM audit.activity_log a
LEFT JOIN auth.users u ON u.id = a.user_id
ORDER BY a.id DESC
LIMIT 20;

7. Cómo se crea esta estructura

De dos formas equivalentes:

  • Desde el backend: al arrancar, la instancia backend-1 crea los schemas que falten (CREATE SCHEMA IF NOT EXISTS), sincroniza las tablas a partir de las entidades de TypeORM y escribe las descripciones. La instancia backend-2 no modifica la estructura, para que las dos no choquen.
  • Con el script database/schema.sql, que crea lo mismo a mano sobre una base vacía.
